# QAD / MFG:PRO Modern Terminal

Windows向けのCustomTkinter製SSHターミナルです。QADのCUI操作、99.7.1.1の受注入力、レポート抽出・GAS転送を扱います。

本READMEは2026-09-29時点のコードと調査結果をまとめています。**注文入力の「送信」はQADへ実際にキーを送ります。** F3の事前表示やローカル試験の成功だけでは、サーバー上の登録成功を保証しません。

## 起動と依存関係

`自作モダンターミナル.pyw`、`terminal_core.py`、`order_entry.py`、`order_history.py`、`order_date_picker.py`、`ui_fonts.py`、`qad_report.py`、`addon_host.py`、`addon_kit.py`、`requirements.txt`と`addons`フォルダを同じフォルダに置きます。会社のVPN接続が必要です。アプリは起動後に自動接続するため、GUI起動もオフラインテストとは区別してください。

Windows 11で初めて使用する場合は、Python 3.12（Python launcher・tcl/tkを含む）を導入し、配布フォルダを展開してから **`初期セットアップ.bat`をダブルクリック**してください。必要なPython環境`.venv`とライブラリを用意し、読み込みまで確認します。管理者権限は通常不要です。初回はインターネット接続が必要です。

配布時はbatと上記のアプリファイルを同じフォルダに含め、各PCでセットアップしてください。他のPCの`.venv`はコピーせず、顧客・製品マスターなどの利用するデータも配布フォルダに含めます。セットアップ中にQADへのログインは実行しません。失敗した場合はエラーを表示して停止します。再実行時はそのPCの既存環境を利用します。

batの表示は文字コードの違いによる誤動作を防ぐため英語です。`Setup completed successfully.`が表示されれば完了です。

手動でセットアップする場合:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\pythonw.exe "自作モダンターミナル.pyw"
```

通常は`.pyw`のダブルクリックで起動できます。同じフォルダに`.venv`があれば、そのPythonへ自動的に切り替えます。起動エラーをコンソールで確認する場合は`pythonw.exe`の代わりに`python.exe`を使います。

依存ライブラリはCustomTkinter（GUI）、Paramiko（SSH）、pyte（仮想端末）、Pillow、python-dateutil、tkcalendar、Babelです。バージョン指定は[requirements.txt](requirements.txt)を参照してください。

受注送信の経路は次のとおりです。

```text
注文入力UI → collect_order → payload
  → _process_order_submission → run_sales_order_automation
  → SalesOrderAutomationController（画面判定と操作選択）
  → TerminalSession.send（CP932変換・キュー投入）
  → SSHワーカー → QAD

QAD応答 → SSH受信 → CP932逐次デコード → pyte仮想画面
  → 自動操作の画面判定 / GUIの変更行描画
```

送信開始時にpayloadを深いコピーで固定し、画面判定も送信先セッションの`get_screen_text()`を使用します。タブを切り替えても別タブのGUIキャッシュを参照しません。ただし、同じセッションの最新画面を読むことと、目的の入力欄を正しく判別することは別です。

`send()`の成功はキューへの投入を意味し、サーバーでの入力確定やDB保存を意味しません。

## 端末・通信の制約

- QAD接続はVT100、132列×24行を基本とし、画面では80〜132列の表示に対応します。
- 日本語はCP932で扱い、受信境界で分割された文字を逐次デコードします。
- EnterはCR（`\r`）。F1は`ESC OP`です。LFやCRLFへ置換しないでください。
- `Press space bar to continue`への応答は単独のSpaceです。Enterを付けません。
- GUIは変更行を描画し、通信はワーカーへ分離しています。実機での速度改善は未測定です。

## 注文入力と候補データ

注文パネルは右側に表示します。Ctrl単独の2回押し、F2、またはメニューから開閉します。ショートカット変更後は保存された割当を確認してください。F3は出力チェック画面です。通常文字の単独割当には制限があり、利用可能な組合せは設定ダイアログの検査に従います。

- 上部: 顧客名、納品先、Required date、Due date、Purchase Order、Remarks、SO comment。
- 日付表示: `yyyy/M/d (ddd)`。初期値は当日です。
- 明細: Item Code・巾・長さ・本数・価格の5列、最大5行。未使用行は空白にします。
- 顧客名・納品先と1行以上の明細が必要です。本数は正の整数、巾・長さは正数、価格は0以上です。
- Remarks・SO commentは初期値が空白。Purchase Orderとコメント類は任意です。
- 同一製品に異なる単価を設定できないシステム制約を維持します。

「表示 → 注文入力の候補CSV」から顧客・納品先の2列CSVを指定します。見出しは`顧客,納品先`または`顧客名,納品先`。顧客ごとに納品先を1行ずつ記載し、選択した顧客の納品先だけを候補表示します。UTF-8（BOMあり／なし）とCP932に対応し、空欄行や同一顧客内の重複納品先を除外します。

候補CSVとサーバー用コードの解決は別です。`customerInfo.txt`は拡張子がtxtでもJSON形式です。マスターはアプリと同じフォルダへ配置してください。コードには作業ディレクトリと旧環境の固定パスへのフォールバックも残っています。顧客名を選べることだけでは、顧客コード・納品先コードが正しく解決された証明にはなりません。

payloadには名称、顧客・納品先コード、住所、日付、PO、コメント、`items`を渡します。日付はISO形式、巾・長さ・価格は小数精度を保つ文字列、本数は整数です。

## 受注自動操作の現行フロー

| 段階 | 現行動作 |
| --- | --- |
| 採番 | Order欄が空の場合にF1を送信し、番号とSold-Toの表示を待つ |
| ヘッダー | Sold-To、Bill-To（顧客コードと同値）、Ship-Toを順に入力 |
| 日付・PO・備考 | Order Date（実行当日）、Required、Promise空、Due、Perform空、Pricing空、PO、Remarksの8項目をCR結合し、F1 |
| 税・販売情報 | 該当画面を判定してF1で進む |
| SO comment | 空ならF4。入力ありなら編集・既定内容の消去操作・本文送信・確定を行う |
| 明細 | 製品→長さ→幅・本数の階層で入力し、Site（既定CB2）、価格、税・コメントを処理 |
| 理由コード | 検出時に70、28、28を固定順で送信する箇所がある |
| 合計・終了 | F1 → F1 → Space。追加警告に応答し、合計画面に残る場合のみF4 |

既存受注の明細画面から開始するとStep 6だけを実行し、payloadのヘッダーは反映しません。途中停止後の再実行は自動的な続きの再開ではなく、重複入力の可能性があります。

F3表示と実行はヘッダー生成関数・確定キー定数を共有しますが、F3は予定手順の表示であり、実際の警告や遷移を検証しません。出力チェック画面からの実行も実送信です。

テストランナーは失敗・エラー・スキップ・expectedFailureを成功扱いしません。通常モードの成功は、省略した受入試験の成功を意味しません。結果JSONには`live_server_verified: false`を記録します。

実登録の確認には、実行前の期待値と、サーバーから独立に読み戻した結果を比較します。Order ID、顧客・請求先・納品先、日付、Site、PO、コメント、全明細を確認します。照合の終了コードは0が一致、1が不一致、2が不正入力です。確定状態の証拠や税・丸めは別途確認が必要です。形式・手順は[検証手順](docs/受注送信_検証手順.md)を参照してください。

## 最初の入力先のずれを調べる仕組み

現在の`tests/order_replay.py`は仮想時刻と実際のCP932・pyte処理を使い、合成画面に対する予定外・早過ぎる送信を検出します。実機記録の自動取り込みや、すべての送信で入力先の不一致を検知して停止する機能は未実装です。

今後のデバッグでは、同じセッション・Order IDに対して次を時系列で結び付ける必要があります。

1. 処理段階と想定する入力先。
2. キュー投入と実送出の時刻・送信キー。
3. 受信データ、送信前後の画面、カーソル位置、警告状態。
4. 到着・未到着・判定不能の判定と停止理由。

判定不能のまま次の値を送らず、最初の不一致候補の前後を保存し、その受信記録を遅延込みでオフライン再生する方針です。これは今後の設計であり、今回README更新時に実装した機能ではありません。

## その他の機能と保存情報

GUIは上部にメニューバー・接続操作、中央にターミナル、右側にキー送信ツールバーを備えます。テーマ・文字サイズ・配色を設定でき、ツールバーボタンは指定キーを1回送ります。定義は`terminal_core.py`の`TOOLBAR_GROUPS`と`KEY_SEQUENCES`です。

レポート系には32prnのuuencode・gzipストリームを復元し、ブラウザ経由でGASへPOSTする機能があります。受注登録はSSHのCUI操作であり、このレポート転送とは別経路です。今回GAS転送の実動作は検証していません。

設定はローカルJSONに保存されます。パスワードの`pass_b64`はBase64表現で、暗号化ではありません。コード内に既定接続情報やGAS接続先の定義もあるため、公開資料へ実値を転記しないでください。アプリには回転ログがあり、「入力情報を一切保存しない」という保証はありません。実注文の読み戻しデータはGit対象外の`verification-output/`で扱います。

### 注文ログ

サイドバーの「リセット」右側の「ログ」で、正常完了した注文の送信時データとOrder IDを参照・コピーできます。新しい順の履歴一覧をスクロールして選択し、「更新」で最新の履歴を取得します。
履歴はアプリと同じフォルダの `order_history.sqlite3` に保存します。Git対象外です。バックアップ・PC移行ではこのファイルもコピーしてください。本機能追加前の履歴は自動復元しません。

「編集 → 注文ログの出力形式…」でテンプレートを設定します。変数を選んで「挿入」できます。製品の変数を含む行は、入力した明細行ごとに繰り返します。設定変更は過去の履歴表示にも適用されます。

```text
${顧客名}
${Order ID}
${ItemCode}  ${幅} x ${長さ} x ${本数} @${価格}
${Required Date} ${納品先}着 で手配しました。
```

日付変数は `2026年10月2日 (金)` の形式です。顧客・納品先・各コード・住所・Purchase Order・Remarks・SO comment・Required Date・Due date・Order IDと、Item Code・幅（巾）・長さ・本数・価格を使用できます。
失敗・中断した送信は完了履歴に追加しません。実際の入力処理は変更せず、完了後にデータを保存します。

同じ製品が連続する行では製品名の表示幅に合わせた空白を残し、幅の開始位置を揃えます。ログ本文はYu Gothicで先頭から表示し、重複する製品行は文字幅を測ったタブ位置で揃えます。ショートカット・デモ注文・update・カラーパレットは「ツール」メニュー内にあります。


### Due Date / Required Date の共通ピッカー

F2サイドバーのどちらの日付欄からも同じピッカーが開きます。上部のDue Date / Required Dateで編集対象を切り替え、カレンダーで選択すると次の項目へ移ります。両端は濃い色、区間は淡い色で表示します。前後関係を変えてもDue DateとRequired Dateの項目を入れ替えません。
両方とも `yyyy/mm/dd` の直接入力が可能で、Enterで入力を反映します。「決定」で2項目をまとめて適用し、キャンセル・Esc・パネルを閉じる操作では未確定の変更を破棄します。矢印キーで日を移動し、Page Up / Page Downで月を移動できます。

追加ライブラリを取得するため、更新後に一度実行してください。

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

`tkcalendar==1.6.1`を使用し、CustomTkinterで操作部を整えています。範囲の色付けは表示中の最大42日だけを対象にするため、長い区間でも全日付を生成しません。

メニュー・サイドバー・ダイアログ・カレンダー・F3の出力チェック画面・注文ログのフォントはYu Gothicです。QADの画面だけは、罫線を揃えるため以前と同じ等幅フォント（Consolas。無い場合はCascadia Mono等）を使います。Yu Gothicは文字ごとに幅が違うため、F3の項目名と値の列は文字幅を測ったタブ位置で揃えています。


## アドオン（クイックメニュー・データ送信の各ボタン）

クイックメニューとデータ送信のバーは本体の機能で、そこに並ぶ「OrderBooking出力」「在庫送信」「Complaint送信」「受注残＆売上送信」は、それぞれ`addons/`フォルダの1ファイル＝1アドオンです。起動時にファイル名順に読み込み、その順でボタンとメニューに並びます（先頭の番号で並び順を調整できます）。

「ツール → アドオン」でボタンごとに次の操作ができます。再起動は不要です。

- **表示・非表示**：チェックを外すとそのボタンだけが消えます。ボタンの右クリック「このボタンを非表示にする」でも同じです。設定は`terminal_config.json`の`addons_visible`に保存され、次回も同じ状態で起動します。非表示のボタンは、割り当てたキーボードショートカットやショートカットバーの99.7.6.20からも実行されません。実行中の送信は最後まで続きます。バーのボタンがすべて非表示になるとバー自体も隠れます。
- **追加**：「アドオンを追加...」で`.py`ファイルを選ぶと、読み込みを確認してから`addons/`にコピーし、すぐにボタンが現れます。読み込めないファイルや、同じIDのアドオンは追加しません。
- **削除**：「アドオンを削除」から選ぶと、ボタンを外してファイルを`addons/_removed/`へ移動します。元に戻すときは、そこから「アドオンを追加...」で選び直すか、`addons/`へ戻します。
- **ボタン名**：「ボタン名の設定...」またはボタンの右クリックで変更・初期化できます。以前に変更した在庫・Complaint・受注残＆売上のボタン名はそのまま引き継ぎます。

データ送信の3つのボタンは同じ排他グループに属し、1つが送信中の間は他の送信ボタンも押せません（サーバー側の32prnの衝突を防ぐため）。読み込みに失敗したアドオンはメニューに「（読み込みエラー）」と表示され、理由は`logs/terminal_debug.log`に残ります。アプリの起動は止まりません。

アドオンファイルの最小構成は次のとおりです。`api`は本体の必要な操作だけを公開し、背景スレッドから呼んでも画面更新はTkのスレッドで実行されます。

```python
ADDON = {"id": "my_report", "name": "自作レポート送信"}

def register(api):
    def run():
        api.set_status("実行中...", "working")
    api.add_button("run", "レポート送信", run, bar="data", color="#059669", busy_group="gas_transmission")
```

主な`api`は、ボタン追加（`bar="quick"`/`"data"`、`requires_connection`、`busy_group`）、ステータス・ログ・エラー表示、背景実行、排他（`begin_busy`/`end_busy`）、設定の読み書き、QADログイン情報、表示中タブの画面判定とタブを固定した送信です。GASへ送るレポートは`addon_kit.py`と`qad_report.ReportShell`を使うと、既存の3つと同じ手順で書けます。アドオンはログイン情報を使えるため、配布フォルダには信頼できるファイルだけを置いてください。

ボタンは`addon_<アドオンID>_<ボタンID>`という名前の枠に置くため、アドオンを追加・削除してもキーボードショートカットの割り当て先は変わりません。アドオン化より前にこれらのボタンへ割り当てたショートカットは、一度だけ割り当て直してください。

既存の機能は次のように改善しています。QADへ送るキー列と固定待ち時間は変更前と同一です。

- 背景処理からのステータス・ダイアログ更新をTkのスレッドへ受け渡します（設計書2.8）。
- データ送信のログインで、メインメニュー表示がパケットに分かれても検出し、表示されない場合は後続のキーを送らずに停止します。変更前は在庫・受注残・売上で確認できないまま続行していました。
- 32prn受信の終端検索をヘッダー以降の新着分に限定しました。大きなレポートでも全体を繰り返し走査せず、ヘッダーより前の文字を終端と誤認しません。終端の直後に制御文字が続く場合の解凍失敗も解消しました。
- 待機中の進捗表示を4秒に1回に抑えました（変更前は該当秒に約20回更新）。
- Complaintの入力値を送信前に検査します。日付が読めない、開始日が終了日より後、Item code・ロットに空白や全角文字がある場合は、QADへ送らずダイアログに理由を表示します。実行中はダイアログを閉じられません。
- GAS転送用の一時HTML（レポートデータを含む）は、次回送信時に1時間以上前のものを削除します。
- OrderBooking出力は、メインメニュー復帰・99.7.6.20画面・Output欄のいずれかを確認できない場合、続行せずに停止します。操作中にタブを切り替えた場合も中止し、二重起動を防ぎます。
- 重複していた32prn解凍・レポート解析の関数を1つにまとめました（実際に使われていた定義を移しています）。

検証は、偽のSSHシェルと仮想時計による回帰テスト（`scripts/check_addon_keystrokes.py`、`tests/check_addon_ui.py`も含む）（`tests/test_qad_report.py`、`tests/test_addon_host.py`、`tests/test_addons.py`）、変更前のワーカーと新しいアドオンに同じ偽応答を与えた送信キー・固定待ちの一致確認、SSHを遮断した画面確認です。実際のQADからの抽出とGASへの転送は、VPN接続時に確認してください。


### 汎用GASでシートへ書き込むアドオン

既存の在庫送信・Complaint送信・受注残＆売上送信は、それぞれ専用のGASへ送る現在の方式のまま動きます。新しく作るアドオンは、書き込み先のスプレッドシートIDとシート名をアドオン内で指定し、汎用GAS（`gas/sheet_writer.gs`）へ送れます。汎用GASは指定シートの値をすべて消してから、抽出結果をA1から書き込みます。

1. `gas/sheet_writer.gs`を新しいGASプロジェクトに貼り付け、ウェブアプリとしてデプロイします（既存のGASはそのまま）。
2. 「ツール → アドオン → シート書き込みGASのURL設定...」に、デプロイしたURL（`…/exec`）を設定します。`terminal_config.json`の`sheet_writer_gas_url`に保存されます。
3. `addon_templates/sheet_report_template.py`をコピーし、`ADDON`、`SPREADSHEET_ID`、`SHEET_NAME`、`extract`（レポートの条件入力）を書き換えます。
4. 「ツール → アドオン → アドオンを追加...」で選ぶと、データ送信のバーにボタンが出ます。

送信内容は`{"spreadsheetId": ..., "sheetName": ..., "data": 行データ}`です。IDの形式が誤っている、またはシート名が空のアドオンは「読み込みエラー」になります。URLが未設定の場合は、QADへ接続する前に止まります。アドオンごとに別の汎用GASを使う場合は`add_sheet_report_button(..., gas_url="…/exec")`を指定します。新しいボタンも既存の送信ボタンと同じ排他グループに入り、同時には送信しません。
