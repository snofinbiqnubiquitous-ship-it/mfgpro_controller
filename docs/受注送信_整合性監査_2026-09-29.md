## 1. 事前表示が正しくても結果が変わる理由

F3の画面は `OrderOutputTerminalWindow.append_submission()` が作る**予定手順の説明**である。
`SalesOrderAutomationController` をサーバー応答に対して実行しているわけではなく、登録値の照合もしていない。
「送信」ボタンは `_process_order_submission()` → `run_sales_order_automation()` から実送信する。
過去のF3表示にあった「実送信は行わない」は現行の動作と異なるため修正した。

実際の処理経路は次のとおり。

1. 入力値をpayloadに変換する。
2. ワーカースレッドが画面文字列を判定してキーストロークを選ぶ。
3. `TerminalSession.send()` がCP932に変換し、送信キューへ追加する。
4. SSHワーカーがキューから送る。戻り値はサーバー側での入力確定・DB登録を意味しない。
5. 受信データを同じセッションのpyte画面へ反映し、GUIは差分を描画する。

このため、「送ったキーが正しい」「画面が遷移した」「入力値がDBに保存された」は別の確認である。

- 同じpayloadをもう一度送ると、どこまで確定したかを知らずに明細先頭から入力するため、重複・既存受注への誤入力が起こり得る。
- `self._is_running_order_automation`は同時実行を抑止するが、既存のキー送信・別マクロすべてを排他制御しているわけではない。
- 対策候補: Order ID、確定済みLn/SL/Ser、処理段階を記録し、再開前にサーバー表示と照合する。自動リトライで新規採番しない。

### P1: 入力値の検証と端末送信の検証が異なる

- `collect_order()`は名称と数値を検証するが、顧客コード・納品先コードの解決結果が非空で正しいかは必須検証していない。

- 対策候補: 採番前に、コード解決・全送信文字列のCP932変換・フィールド別の制御文字とバイト長を検証する。SO commentの行区切りと単一行のRemarksは区別する。実サーバー側の最大長は未確認。

### P2: 完了画面は登録値の一致を意味しない

- 完了条件にはMain Menuまたはヘッダー表示が使われ、明細件数・数量・単価・納期・コメントの保存結果を読み戻していない。

## 5. 共通の記録と判定基準

### 5.1 一つの時系列に残す情報

| 記録 | 必須内容・目的 |
| --- | --- |
| 実行識別 | run ID、コードのコミット、環境識別子、session ID・接続世代、Order ID（採番前は未確定）、端末サイズ・文字コード |
| 操作識別 | operation ID、処理段階、対象フィールド、明細のLn/SL/Serまたは入力行、直前操作との関連 |
| 時刻・順序 | 単調増加時計による経過時刻とイベント連番。人が照合する開始日時も保存。異なる端末の壁時計だけで前後関係を決めない |
| 判断 | 想定状態、観測状態、入力先、警告、採用した根拠、READY／WAIT／WARNING／UNKNOWN／STOP、許可・禁止した操作 |
| 送信 | 意図したキー／値、CP932変換後のバイト列、キュー投入時刻、SSH送信呼出の開始・結果・バイト数。部分送信なら各範囲を関連付ける |
| 受信 | 受信時刻、バイト列と順序、デコーダー／pyte反映後の更新番号、画面とカーソル位置・可視状態 |
| 停止・完了 | 最初の違反イベント、停止理由、待機期限、未送信キュー・送信中の操作、最後に確認できた入力先 |

画面・カーソル・更新番号は同じセッションから一貫したスナップショットとして取得する。更新番号が増えたことだけを新しい入力要求とは扱わない。SSH APIが送信を受け付けたことも、サーバー処理完了とは区別する。

再生には開始時の画面・カーソル・必要な端末状態と、その後の受信順序が必要。画像や画面テキストだけでは制御シーケンス・部分更新を復元できない。認証完了後の検証開始点を決め、初期状態を再現できない記録は再現性不足とする。

原本ログは認証情報を含めず、実注文データを含む記録はローカルの`verification-output/`に保存する。共有する再現用データはCP932のバイト幅・カーソル位置を壊さず匿名化し、原本と区別する。ログ欠落・上限到達時は完全な記録として扱わない。

### 5.2 「入力できる」の根拠を先に定める

各状態について、状態ID、識別する画面・ポップアップ、対象欄、確認済みカーソル範囲、警告の有無、許可する操作、次にあり得る状態、期限、根拠のログを表にする。座標は実機資料から決め、未確認の値を補わない。座標の0/1始まりと端末サイズを明記する。

- READY: 対象画面・入力欄を示す複数の根拠が一致し、未処理警告がない。送信後の到着確認には、その操作後の応答と状態遷移の証拠がある。
- WARNING: 現在アクティブな警告要求を確認できる。通常の背景ラベルより優先する。
- WAIT: 遷移中または応答待ち。次の入力値は送らない。
- UNKNOWN: カーソルを取得できない、画面が未知、根拠が矛盾する等。代替の確認済み根拠がない限りREADYへ昇格させない。
- STOP: 期限超過、切断、不一致等で続行不可。自動再送・新規採番をしない。

ラベルの存在、一定時間の無受信、カーソル位置、画面の安定、受信更新のいずれか一つだけではREADYの証明にしない。非同期受信と送信の間には競合が残るため、判定に用いた更新番号と送信境界を記録し、キュー待ち中に状態が変わったケースも検証する。

正常な応答では期限内に次へ進むことも合格条件にする。「すべて停止する」だけでは合格にしない。正しい操作は現行コードの出力から逆算せず、確認済みログ・操作仕様または明示した合成シナリオで先に定義する。

## 6. 3点を検証する試験指針

### A. 画面遷移が終わる前に次の値を送っていないか

対象はSold-To→Bill-To→Ship-To、ヘッダー8項目、製品・Site、長さ・本数・幅、コメント行、理由コード、合計画面。初期画面と「実際に次の入力を受け付ける時刻」を試験側で定義し、送信時刻と比較する。

| ID | 再現する条件 | 合否基準 |
| --- | --- | --- |
| A1 | 正常遷移の応答を0／0.1／0.5／1／3秒遅らせる（期限内） | READY前の次項目送信0回、READY後は許可した操作を1回だけ送る |
| A2 | 遷移しない、期限直前・直後に到着、待機中に切断 | 期限と操作順序を記録。未到着なら停止し、遅れて届いた応答で自動再開しない |
| A3 | ラベル→値→カーソルの順と逆順で部分描画、CP932・ESC列を1／2／8バイト・全体で分割 | 同じ完全応答なら同じ最終判定。途中の文字やカーソルだけで次へ進まない |
| A4 | キューに次の値が残る状態で停止、キュー投入後・実送出前に警告や切断 | 停止後に未送出の自動入力が流れない。送信中・送信済みの範囲は明示し、取消済みと偽らない |
| A5 | CR結合したヘッダーの途中、幅・本数の途中に警告を挟む | 後続フィールド用の値が警告や別欄へ流れたら失敗。一括送信は各フィールドの境界でも評価する |

一括送信の開始前に一度READYを確認しても、バイト列内部の後続項目の安全性は保証されない。A5は必要に応じてフィールド単位の送信へ分解する判断材料とする。単にsleepを長くして成功した結果は、遷移確認の証拠にしない。

### B. 画面の文字があるだけで入力可能と誤判定しないか

| ID | 再現する条件 | 合否基準 |
| --- | --- | --- |
| B1 | 同じSold-To／Bill-Toラベルがある2画面で、カーソルと入力欄だけを変える | 正しい入力先の画面だけをREADYとし、違う欄へは送らない |
| B2 | 背景に正常画面を残した警告・ポップアップ | WARNINGまたはUNKNOWNとなり、背景ラベルで通常入力を許可しない |
| B3 | `Category=`だけの画面、引用された警告文、解除途中の警告残像 | Space要求と断定しない。不明なら待機／停止し、推測で応答しない |
| B4 | 古い画面・別タブ・再接続前の通知、送信と無関係な画面更新 | session・接続世代を照合し、古い情報や更新番号だけでREADYにしない |
| B5 | カーソルなし・隠れたカーソル、未知レイアウト、端末サイズ変更、空のコード | 明示した代替根拠がなければUNKNOWN。空文字の包含判定を成功理由にしない |

試験側の正解状態は、実装のラベル判定関数を再利用して作らない。正常画面と紛らわしい画面を対にし、「正しいときに進める」「違うときに止まる」の両方を確認する。

### C. 警告や確定操作を固定キー列で処理していないか

| ID | 再現する条件 | 合否基準 |
| --- | --- | --- |
| C1 | 1回目F1で警告へ進む | 2回目F1を自動送信しない。確認済みSpace要求ならSpaceだけを1回送る |
| C2 | F1後、警告なしでMain Menu／Order空欄へ復帰 | その時点で終了扱いなら余分なSpace・F1・F4を送らない。必要なメニュー復帰が別仕様なら状態に対応付ける |
| C3 | Space後の警告消去を0.9秒以上遅らせ、同じ警告を再描画 | 同じ警告要求への重複応答0回。待機期限を超えたら停止 |
| C4 | 警告解除後に同じ文面の新しい警告、または異なる警告が続く | 別の要求と確認できたものだけに各1回応答。文面のハッシュだけで同一／別と決めない |
| C5 | 理由コード欄が0／1／2／3個、途中で未知の欄へ進む | 確認済みの欄に対応する値だけを送る。固定の70→28→28を使い切ることを成功条件にしない |
| C6 | 合計画面の状態別にF1／F4が異なる応答を用意 | 各状態の証拠で定義したキーだけを許可。正解が未確認の分岐は「未判定」で、適当なキーを選ばない |

警告の同一性は「応答を送った」「要求が消えた／別状態へ移った」「新しい要求が現れた」という経緯で管理する。同じ表示のまま別要求へ移ったか区別できない場合は判定不能とする。更新番号が変わっただけでSpaceを再送しない。

現行のF1→F1→Spaceと過去ログのF1→F4→F4は、両方を無条件に正解とするのではなく、各キー直前の合計欄・警告・Order欄・カーソルと対応付ける。対象環境の根拠が揃うまでC6の実機適合は未確定とする。

## 7. 検証の進め方と最初の不一致の報告

1. **既存証拠を整理する。** 上記6件と既存ログを使い、確認済み・合成・不明の状態を分ける。既存試験で足りる条件は新設しない。
2. **オフラインで再現する。** A〜Cの正常系・異常系を試験側の仮想時刻で進め、予定外キーを即失敗にする。実装がキーを送ったから画面を成功へ進めるモックにしない。最初は各条件を単独で、その後「遅延＋背景ラベル＋警告」等を組み合わせる。
3. **送信経路まで確認する。** コントローラの送信要求だけでなく、キュー待ち・部分送信・切断・停止の条件も含める。既存リプレイだけではSSH送出境界まで確認できない。
4. **実機の不足分を埋める。** VPNと利用許可のある検証環境・対象Order IDで、記録機能と停止処理を準備してから取得する。今回の文書更新ではログインや注文登録を行わない。採番・再送を繰り返す調査はしない。
5. **記録を再現ケースへ戻す。** 初期状態・受信データ・遅延と期待状態を保存し、同じ最初の違反が再現するか確認する。バグ修正で送信経路が変わる場合、元の録画を無条件に流し続けず、操作ごとの許可応答を定義し直す。録画にない分岐は未検証とする。
6. **実登録を独立に照合する。** 詳細は[検証手順](受注送信_検証手順.md)を使用する。入力先の一致とDB登録値の一致は別の合格項目にする。

最初の不一致の報告には、次のテンプレートを使用する。

| 項目 | 記入内容 |
| --- | --- |
| 再現条件 | A/B/CのID、実機／合成、コード・環境・run ID |
| 最後に確認できた状態 | イベント番号、画面とカーソル、入力先、操作 |
| 最初の違反 | イベント番号と経過時刻、想定入力先、観測入力先または判定不能 |
| 証拠 | 直前の送信意図・キュー投入・実送出、受信範囲、前後画面、判定に使った根拠 |
| 影響 | 次の値を送ったか、送信済み／未送信の範囲、サーバー保存の確認有無 |
| 分類 | A:到着前送信、B:状態誤認、C:不要キー、複合、証拠不足。無理に一つへ限定しない |
| 再現・修正確認 | 使用したケース、修正前の失敗点、修正後の合否、未確認事項 |

「Bill-Toの表示前に送った」だけで結論付けず、クライアントが把握できた状態と、試験側または実機証拠が示す状態を比較する。受信順序だけで原因を断定できない競合は、候補として記録する。

## 8. 合格条件と今回の更新範囲

- 正常ケースで必要な操作が過不足なく進み、A〜Cの異常ケースでは禁止キー・別欄への値が送出されない。
- 遷移失敗・不明状態・切断で停止し、未送信キューからの漏れと自動再送がない。送信済みの内容は取消し扱いにしない。
- 既存6件と追加ケースの結果・証拠を残す。未実施・未判定・スキップを合格に数えない。
- 最終キーの相違が状態別の実機証拠で説明でき、許可された実登録の読み戻しも一致する。実機未実施ならオフライン条件の合格範囲だけを記す。

過去の結果は初回39件成功、追加後57件中51件成功・6件失敗。今回それらを再実行したわけではない。本改訂は整合性監査の上書きのみで、記録機能・停止機能・追加テスト・本体コードの実装は別作業とする。同一製品・異単価に関する仕様も変更しない。
