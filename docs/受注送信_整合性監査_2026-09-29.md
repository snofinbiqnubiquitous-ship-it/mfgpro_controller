# 受注送信の事前表示・実行・調査ログの整合性監査（2026-09-29）

> 追加の試験プログラム・実行方法・失敗6件の再現条件は[受注送信の検証手順](受注送信_検証手順.md)を参照。下記39件は最初の修正時の結果で、追加後は57件中51件成功・6件失敗。

対象: `186a968` を基準にした `order_entry.py`、`terminal_core.py`、`自作モダンターミナル.pyw`。
引継ぎ設計書、既存モックテスト、保存済み実機ログを照合した。今回、SSH接続・新規採番・実注文の変更は行っていない。

## 1. 事前表示が正しくても結果が変わる理由

F3の画面は `OrderOutputTerminalWindow.append_submission()` が作る**予定手順の説明**である。
`SalesOrderAutomationController` をサーバー応答に対して実行しているわけではなく、登録値の照合もしていない。
「送信」ボタンは `_process_order_submission()` → `run_sales_order_automation()` から実送信する。
過去のF3表示にあった「実送信は行わない」は現行の動作と異なるため修正した。

実際の処理経路は次のとおり。

1. 入力値をpayloadに変換する。
2. ワーカースレッドが画面文字列を判定してキーストロークを選ぶ。
3. `TerminalSession.send()` がCP932に変換し、送信キューへ追加する。
4. SSHワーカーがキューから送る。戻り値はサーバー側での入力確定・DB登録を意味しない。
5. 受信データを同じセッションのpyte画面へ反映し、GUIは差分を描画する。

このため、「送ったキーが正しい」「画面が遷移した」「入力値がDBに保存された」は別の確認である。

## 2. 今回修正した箇所

| 問題 | 旧動作 | 修正 |
| --- | --- | --- |
| 送信先と画面判定の不一致 | 送信先は開始時のsession、判定は現在表示中の`raw_lines`／Textbox。途中のタブ切替で別画面を読む可能性 | `TerminalSession.get_screen_text()`を追加し、送信先sessionの画面をロック下で取得。GUIのdirtyフラグは消費しない |
| 実行中のpayload変更 | ワーカーが渡された辞書を直接参照 | 開始時に深いコピーを作成し、実行対象を固定 |
| エラーが表示されない | `except ... as te/ex`の変数を遅延実行するlambdaが参照。except終了後には変数が消えている | エラー文字列をlambdaのデフォルト引数で保持 |
| ヘッダー生成が二重管理 | 実行とF3表示で日付変換と8項目の並びを個別実装 | `build_order_header_fields()`を共有。Promise/Perform/Pricing Dateの空スキップを維持 |

## 3. 未解決の問題・エラーが出る条件

以下は今回すべてを改修したという意味ではない。実機の入力状態を示す情報が不足する部分は、推測によるキー変更を避けて記録する。

### P1: 最終確定手順の資料とログが一致しない

- 現行 `execute_step6()` は合計画面で `F1 → F1 → Space`。合計画面に残っている場合のみF4を送る。
- 引継ぎ設計書3章もこの手順を記載している。
- `scratch/order_test6_execution.log` の837行付近はF1、866行付近はF4、895行付近は最後のF4と記録している。
- 同ログの `29_STEP630_FRAME_2PLUS` にはカーソル `row=24, col=79` が記録され、F4の後にはOrder空欄のヘッダー、その次のF4の後にはMain Menuが記録されている。
- **今回、実送信のキー順序は変更していない。F3表示が現行コードと一致したことは、現行キー列がサーバーで正しいという証明ではない。**
- 次の確認では、合計画面の上段・下段・警告・Order空欄の各状態で必要なキーを区別する。1回目F1で既に確定・警告へ進む場合に2回目F1を送ってよいか、警告なしでSpaceを送ってよいかは未確認。

### P1: 同じラベルが常駐し、待機条件が入力可能状態を証明しない

- Step 2のSold-To送信後は、顧客コードと`Bill-To`の文字があるだけでループを抜けられる。どちらも古い画面に残り得る。
- Order Date待機は `order date` **または** `order:` **または** 納品先コードを含めば成立する。空の納品先コードは常に文字列に含まれるため、コード未解決の入力ではさらに弱くなる。
- Step 6の `item number`、`site`、`sales order line` も背景の常駐ラベルで成立し得る。
- 同一セッションの最新バッファを読む今回の修正は参照先の問題を解消するが、カーソルが目的フィールドへ移動したことまでは保証しない。
- 対策候補: ラベルだけでなく、ポップアップ境界・カーソル位置・フィールド値・送信後に発生した受信更新を組み合わせて状態を判定する。座標は実機ログから状態別に確認し、推測で固定しない。

### P1: 固定待機・一括送信が「先走り禁止」の設計方針と矛盾

- ヘッダー8項目のCR連結送信、ロール本数・幅、理由コード`70 → 28 → 28`、特記事項の各行、最終F1/Spaceで固定時間の待機が残る。
- 警告の出現・処理速度・必要な理由コード欄が変わると、後続キーが別フィールドに入る可能性がある。
- Step 2の25回ポーリングは時間切れでも例外を出さず、そのままBill-To入力へ進む。
- 対策候補: 目的フィールドへの遷移を確認できない場合は停止する。入力欄が少ない場合に余った理由コードを送り込まない。既存待機を一律に短縮しない。

### P1: 警告表示と通常画面の判定順序

- `wait_for_screen()` は成功条件を先に評価する。背景ラベルが成功条件を満たすと、その上に警告があっても通過する。
- 逆に `category=` だけでもSpaceを送り、同じ古い警告が残れば繰り返す。受信の遅延で余分なSpaceが次の欄に入る可能性がある。
- 対策候補: アクティブな警告を優先判定し、同じ表示世代への応答は1回に制限する。異なる警告が同じ文面を使う場合も考慮する必要がある。

### P1: 中断後の再送信は再開処理ではない

- 明細画面にいる場合はStep 6だけを実行するため、payloadの顧客・納品先・日付・POなどのヘッダーを反映しない。
- タイムアウトしても、サーバーへ既に送られた文字や登録済み明細は取り消されない。キュー内の残りも別途考慮が必要。
- 同じpayloadをもう一度送ると、どこまで確定したかを知らずに明細先頭から入力するため、重複・既存受注への誤入力が起こり得る。
- `self._is_running_order_automation`は同時実行を抑止するが、既存のキー送信・別マクロすべてを排他制御しているわけではない。
- 対策候補: Order ID、確定済みLn/SL/Ser、処理段階を記録し、再開前にサーバー表示と照合する。自動リトライで新規採番しない。

### P1: 入力値の検証と端末送信の検証が異なる

- `collect_order()`は名称と数値を検証するが、顧客コード・納品先コードの解決結果が非空で正しいかは必須検証していない。
- Remarksは複数行入力できるが、ヘッダーの1フィールドにそのまま埋め込まれる。改行・タブ・ESCなどを含む値は端末操作として解釈される可能性がある。
- CP932に変換できない文字は`TerminalSession.send()`で失敗する。前の項目を送信した後に初めて失敗すると、部分入力が残る。
- 対策候補: 採番前に、コード解決・全送信文字列のCP932変換・フィールド別の制御文字とバイト長を検証する。SO commentの行区切りと単一行のRemarksは区別する。実サーバー側の最大長は未確認。

### P2: 完了画面は登録値の一致を意味しない

- 完了条件にはMain Menuまたはヘッダー表示が使われ、明細件数・数量・単価・納期・コメントの保存結果を読み戻していない。
- ヘッダー復帰判定はOrder欄が空であることまでは要求していない。Order ID抽出も広い正規表現に依存する。
- 成功表示だけでは「入力内容と登録結果が一致した」と判断できない。既存ログ・モックテストが通っていても同様。

## 4. 検証方法の不足と次に必要な証拠

既存 `tests/test_step6_order_automation.py` のモックは送信キーで即時に画面を進め、多くのテストでsleepを無効化している。
未定義のキーを無視するモックもあり、誤送信を受けてもテストが成功する場合がある。
`test_630_space_prompt_after_first_f1` は名前・コメントでは1回目F1後の警告と説明するが、実際のモックはF1が2回になるまで警告へ進めない。
このため「1回目のF1だけで警告に進むケース」の検証証拠として使わない。

今後必要なのは、任意のsleepを長くすることではなく、以下の区別を持つ応答リプレイと登録内容の確認である。

- キーのキュー投入・実送出・受信更新・カーソル・画面状態を、同じsessionとOrder IDにひも付けて記録する。
- 遅延受信、複数パケットの部分再描画、背景ラベルが残る警告、切断、予定外キーを再現する。
- 予定外のキーを無視せずテストを失敗させる。部分入力後の再送が追加登録にならないことを確認する。
- 最後に、許可された単一の既存Order IDについてヘッダー・明細・コメントを読み戻す。今回この実サーバー照合はしていない。

今回追加した `tests/test_order_consistency.py` は、タブ切替時の参照先固定、payload固定、遅延エラー通知、GUI差分を消費しない画面取得、F3表示の整合をオフラインで検証する。
これらはサーバー上の入力プロトコルやDB登録結果の検証を代替しない。
