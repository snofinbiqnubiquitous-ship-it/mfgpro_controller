# 受注送信の検証手順とテストプログラム

## 結論と現在の結果（2026-09-29）

「事前表示が正しい」だけではサーバー登録結果の一致を保証できない。以下の3段階が必要。

1. **回帰試験**: 入力の変換、送信先固定、表示、CP932・VT100受信、送信順序、照合プログラムを検証する。
2. **受入条件試験**: 遅延・警告・画面遷移失敗があっても余分なキーを送らないことを確認する。
3. **実サーバー読み戻し**: 独立に取得した確定済み注文のヘッダー・全明細・コメントが入力と一致することを確認する。

今回の実行結果は **全57件中51件成功、6件失敗、エラー0件**。失敗は2段階目の未解決条件であり、`expectedFailure`で合格扱いにはしていない。
**現状は受入条件が未達。実サーバーの注文登録を完全に検証済みとは扱えない。** 今回はSSH接続・GUI起動・採番・注文更新を実行していない。
同一製品に異なる単価を設定できないシステム制約は維持している。

## 1. オフライン試験の実行

リポジトリ直下で実行する。下記プログラムはログイン・サーバー更新を行わない。`scratch`配下の実機用スクリプトをテスト探索に含めない。

```powershell
# 回帰試験のみ（51件）
.\.venv\Scripts\python.exe -X utf8 scripts/verify_order.py --report verification-output/regression.json

# 未解決条件を含む全試験（57件、現状は終了コード1）
.\.venv\Scripts\python.exe -X utf8 scripts/verify_order.py --acceptance --report verification-output/acceptance.json
```

- 終了コード0: 選択した試験は成功。省略した受入試験・実機試験まで成功した意味ではない。
- 終了コード1: 失敗・エラー・スキップ・expectedFailureのいずれかあり。JSONの`failures`／`errors`等を確認する。
- 出力JSONはモード、件数、失敗テスト名・詳細、`live_server_verified: false`を記録する。
- `verification-output/`はGit対象外。注文の読み戻し結果や個人の実行結果はここへ保存する。

### テストの構成

| ファイル | 確認すること |
| --- | --- |
| `tests/test_order_consistency.py` | タブ切替後の送信先固定、入力内容の固定、遅延エラー通知、F3表示と共通ヘッダー生成 |
| `tests/order_replay.py` | 仮想時刻、遅延受信、画面再描画、切断、予定外／先走り送信を即時失敗させる再現基盤 |
| `tests/test_order_replay.py` | CP932とESCを1バイトずつ受信、Space単独の警告応答、切断・中断・タイムアウト、単一明細の全送信キー照合 |
| `tests/order_acceptance_cases.py` | 下記6つの未解決条件。通常の`test_*.py`探索には含めず、`--acceptance`で必ず実行する |
| `tests/test_order_result_comparison.py` | 登録結果比較の正常系、各項目相違、重複・不足明細、不正入力、未確定状態の検出 |
| 既存の入力・Step 6テスト | 数値変換、明細の複数製品・長さ・幅、特記事項、従来の自動入力フロー |

再現基盤は実際の`TerminalSession.feed()`を使い、CP932デコードとpyte画面処理を通す。ただしSSH接続・送信キュー・サーバー処理そのものは再現しない。
画面は合成データであり、実機の状態を網羅した記録ではない。仮想時刻はsleepを即座に消すだけではなく、指定時刻まで応答を届けない。
現行モックのように予定外のキーを無視せず、キーの不一致・応答前送信・未実施の必要キーで失敗する。

### 今回失敗した6件

| テスト名の末尾 | 再現条件 | 検出した現行動作 |

特に最終確定キーの正解は、[監査資料](受注送信_整合性監査_2026-09-29.md)に記載したF1/F4の実機ログ差異を調査して決める。テストを成功させるためだけにモックの期待値を現行コードへ合わせない。

## 2. サーバー登録結果を照合する

`scripts/compare_order_result.py`は2つのJSONを読み、Order ID、Sold-To、Bill-To、Ship-To、Order Date、Required/Due Date、Site、PO、Remarks、SO comment、全明細を比較する。
明細は製品・幅・長さ・単価・Siteごとに本数を集計し、サーバー側のLn/SL/Ser分割や表示順に左右されず比較する。製品コードの`group_order_items()`を再利用せず、変換ミスの共倒れを避ける。

合成サンプルで起動・フォーマットを確認する:

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts/compare_order_result.py tests/fixtures/order_readback_expected.json tests/fixtures/order_readback_actual.json
```

この例は`match`／終了コード0になるが、**サンプル同士の一致であり、実機確認ではない**。

実際の照合:

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts/compare_order_result.py verification-output/expected.json verification-output/actual.json
```

- `expected.json`: 実行前に保存したpayloadを基に、今回のOrder ID、Bill-To（現行仕様は顧客コードと同値）、実行日の`order_date`（ISO）、実際に使用する`site`を明示する。結果を見て期待値を書き換えない。
- `actual.json`: サーバーの既存レポート・許可済みの読取手段から**独立に**取得したデータを、サンプルと同じ形式へ変換する。`expected.json`やF3の表示をコピーして作らない。
- 全必須文字列を含める。空のPO・Remarks・SO commentも`""`を明示する。日付は`yyyy-MM-dd`。
- サーバーの確定状態を確認できた場合のみ`committed: true`を設定する。このフラグを手入力しただけでは確定の証拠にならない。元の読取結果、取得時刻、対象環境、取得手段もローカルに保存する。
- Ln/SL/Serを1レコード1幅・長さ・本数の`items`へ展開する。各行のSiteも取得する。行の`site`省略時はルートの`site`を適用するため、複数Siteがある実データで省略しない。
- 数値の表示上の末尾0、文字列前後の空白、CRLF/LFの差は正規化する。コメントの内部空白・行順・本文は比較する。
- 数量・品番・寸法・単価の欠落や余分な明細、ヘッダー差異、未確定は終了コード1。欠落フィールドや不正な数値・JSONは終了コード2。
- この比較は論理的な入力値を対象とし、DBのLn/SL番号そのもの、税計算・丸め、内部ステータス全種類、証拠ファイルの真正性を検証しない。これらは下記の実機確認が必要。

DB抽出のテーブル・権限・接続方式はここでは新たに仮定していない。未知のSQLや新規ログインを自動実行する機能は付けていない。

## 3. 実機で残る確認項目

オフライン受入条件を修正した後、検証用環境または**利用が許可された単一の検証用Order ID**で行う。以前のVPN制約は継続しており、今回は実施していない。
新規採番を繰り返して検証しない。他人の受注を検証用として選ばない。

1. 実行前の注文状態・対象環境・Order ID・payload・コードのコミットを保存する。途中の既存受注を使うと現行コードはStep 6から開始しヘッダーを反映しないため、確認対象がヘッダー込みか明細だけかを区別する。
2. 対象環境に適した開始画面で一度だけ実行し、送信時刻と受信バイト、カーソル、画面、Ln/SL/Serを同じOrder IDへ対応させて記録する。パスワード入力を含むログは採取しない。
3. 別の読取手段で登録値を取得し、上記比較を実行する。Order ID、請求先・納品先、明細合計、税・丸め、理由コード、特記事項の既定行が残っていないことも確認する。
4. 遅延、警告なし／あり、理由コードの種類・数、複数製品・長さ・幅、コメントあり／なし、最大長・半角カナ・日本語を確認する。過去ログがある条件はまず匿名化した応答を再現基盤へ追加する。
5. 切断・中断・同じ注文の再送・別マクロや手動キーとの競合は、**重複登録を防止する設計と復旧手順を先に確定**してから検証する。現状の自動再送を安全とは扱わない。

追加する応答パターンの目安: 遅延0／0.1／0.5／1／3秒／タイムアウト超過、1／2／8バイト／全体の分割受信、警告の出現直前・解除直後・画面更新途中での中断。
現行テストはこの組合せ全体やサーバーのDBトランザクション・再接続・再送排他を網羅していない。未実装の条件を「テスト済み」と記録しない。

## 4. 運用受入の条件

- 回帰試験と受入条件試験が、失敗・エラー・スキップなしで通る。
- 最終確定のF1/F4の違いが対象環境の実機証拠で説明できる。
- サーバーから読み戻した値が一致し、確定状態・税額・合計・重複なしを別途確認できる。
- 部分成功後の再開手順が定まり、再実行で採番や明細を重複させない。

有限のテストで全状態の「完璧」を保証することはできない。確認済み環境・入力範囲・障害条件を記録し、その範囲を超えた変更では対応する試験を追加する。
